- D-008 (2026-10-09) Contrast test (P0-3) found three plan values below AA. Fixes: (a) iOS `glassAccent` light alpha 0.72 → 0.80 (white label 4.12 → 4.91:1 over `bg`); (b) dark `glassAccent` label #FFFFFF instead of onPrimary-style #3A0A14 (2.9:1 → 5.85:1); (c) accent text is only used on `bg` and `surface`; dark accent on `surface2` is 4.21:1, so chips on `surface2` use `textPrimary`. Rejected: another font-to-path library (more dependencies for a sub-1% effect).

- D-011 (2026-10-09) Expo Go shows its own launch screen, not the `expo-splash-screen` config, so the wine splash cannot be seen in Expo Go. P0-4 verifies the config by test and by rendering the assets (docs/screenshots/P0-4-preview.png); the native splash is confirmed on the dev client at P3-8. Rejected: a fake in-app splash screen that would diverge from the real one.
- D-012 (2026-10-09) Plan contradicts itself: §9.8 footer reads "Not for contraception" and onboarding step 4 lists "Hormonal contraception", "Perimenopause", "Irregular cycles (e.g. PCOS)", but §2.3 forbids "contraception", "perimenopause (as a verdict)" and "PCOS". (uses the §2.3 store wording); PCOS is never named in copy ("Irregular cycles" only); the two life-state category labels that the user picks for themselves ("Hormonal contraception", "Recently stopped contraception", "Perimenopause") are exempt from the forbidden-word test only under `onboarding.s4.options.*` and `settings.lifeState.options.*`, and only for those words. Rejected: dropping the labels (users could not set their state, and the engine gates in §4.9 would never fire); softer labels such as "Hormonal method" (unclear to the user).
- D-013 (2026-10-09) Sex logging label is "Condom used" (payload field stays `protected`); copy never uses "protected". Rejected: "Protected/Unprotected" (forbidden word, reads as a safety claim).
- D-014 (2026-10-09) Gap decisions for P0-5: Settings strings and the 24-code symptom list are in `copy/en-AU.json` and `copy/symptoms.json`. The 16 non-default symptoms are: mid_cycle_pain, back_pain, joint_pain, nausea, dizziness, irritability, anxiety, insomnia, appetite_increase, food_cravings, diarrhoea, constipation, hot_flushes, night_sweats, low_libido, high_libido. Flag wording lives in `copy/flags.en-AU.json` and fixed legal wording in `copy/legal.en-AU.json` (the locations named in §11.2). Missing flag wordings (prolonged, intermenstrual, missed, short luteal) written in the §4.10 register: always "a doctor can help you check", no condition named. "Mittelschmerz" is exposed as "Mid-cycle pain" (plain language).
- D-015 (2026-10-09) Fixtures A–I (P0-7). Every plan number was recomputed independently in Python/SciPy from the §4.3/§4.5/§4.8 equations. Posterior mean, ν, scale, 80% intervals, next-period dates and the full A fertile table all reproduce exactly. Findings:
  1. The plan numbers were computed with λ = 1 (prototype), not the default 0.92: fixture A has ν = 8, which needs W = 3. Fixture settings therefore set `recencyLambda: 1` (`fixtures.ts`).
  2. Dates follow `start + round(offset)`; "day N" in the plan means N days after the first bleeding day (day 0). The plan's A point date 30 Oct, B 29 Oct, C 29 Oct, D 3 Nov all follow.
  3. Plan values that do NOT follow the plan's own formulas, where the tests assert the formula value: ovulation SD B 3.9 (formula 3.71), C 5.4 (6.46), D 7.0 (7.17), F 3.6 (3.68); fixture E next-period point 1 Nov (formula 30.43 → 31 Oct; the 80% range 27 Oct–5 Nov matches); fixture G "p ≥ 0.8 on days 10–15" (formula gives 0.69 at days 10 and 15, ≥ 0.93 on days 11–14). Rejected: bending the engine to the plan's prose numbers (no equation reproduces them).
  4. Gap: expected fertile-day probabilities for B, C, D from the §4.8 formula are in `fixtures.test.ts` (days 8, 10, … 22). E: the plan shows a dash for ovulation, but C (0 cycles) shows one, so hiding it at 1 cycle would be inconsistent; the engine shows an ovulation estimate whenever a next period is predicted. E expectations (day 18.0, SD 4.73, fertile 0.16/0.26/0.37/0.45/0.47/0.42/0.32/0.21) are formula values.
  5. Fixture H needs a BBT series and later `today`; G and H use `today` inside the cycle after the biomarker days (day 20 / day 26). Luteal length convention (fixture F): `nextStart - ovulation.point - 1`.
  6. The failing-until-implemented gate (`it.fails` + `IMPLEMENTED` flags) was removed in P1-9 when `predict` went green; all of A–I now run as ordinary tests.

- D-016 (2026-10-09) BBT parameters the plan leaves open (P1-4): CUSUM slack 0.05 °C (reference value k; threshold 0.5 °C-days from the plan), baseline = mean of the first six valid readings, run start = day after the last zero of the statistic; CUSUM "disagrees" only when it crosses and its first-high estimate is more than 2 days from the primary (no crossing is not disagreement, because the primary rule is stricter). Provenance SD factors (§4.7) are applied inside each detector from the readings in the detection window (max factor), not in `combineOvulation`. BBT/wearable confidence is capped at `medium` (`low` on CUSUM disagreement): §4.8 reserves `high` for LH or mucus. Duplicate readings on one day keep the later one. Rejected: slack 0 (random follicular noise crosses 0.5 °C-days), a time-drift correction (V-06).
- D-017 (2026-10-09) Combination details (P1-5). `combineOvulation` returns `OvulationEstimate | null` (null when nothing usable; the plan's signature returns a value). LH runs of > 3 positives are returned with `indeterminate: true` and are ignored by the combiner. The gate and the disagreement rule both apply as written, so a shift at exactly +4 days passes the gate but then disagrees with LH by 4 > 3 days: LH alone, confidence low, conflict recorded. Cervix weight is capped at 25% of the other signals' total weight (the plan says only "capped"). Mucus: the last confirmed patch wins, three consecutive sticky/dry observations are required. Cervix: consecutive-day high/soft/open run of ≥ 2, "closed" observation within 3 days after. Confidence `high` requires an LH or mucus signal among those kept. Rejected: letting a sub-1.5 SD temperature estimate reach `high` (§4.8 reserves it for LH/mucus).
- D-018 (2026-10-09) Life-state interpretation (P1-6). (1) §4.9 "prior only (κ₀ = 0.5, no history)" and "cycles weighted 0.5" are both applied: during the 3-cycle warm-up, cycles that start before the stop/delivery date weigh 0 and later cycles weigh 0.5 (so the prior dominates, new cycles still count). (2) A postpartum state does not mark every later cycle `life_state` (classify only excludes the cycle spanning delivery); the warm-up handles the rest. (3) "Suspended until the first logged period" = no cycle start on or after the delivery date. (4) Engine returns codes (`hormonal_contraception`, `pregnant`, `postpartum`) in `suspended.reason`; wording lives in the UI. (5) Perimenopause suggestion rule (§4.9 "auto-suggested when STRAW+10 early-transition criterion is met at age ≥ 40"): at least two of the last three consecutive-cycle differences ≥ 7 days, from the last four valid cycles. Rejected: using the open-ended `postpartum` state to exclude all later cycles (the warm-up could never run).
- D-019 (2026-10-09) Flag details (P1-7). (1) §4.10 says flags use valid cycles only; §4.14 S2 says skipped-log cycles still count toward long-cycle flags. Both kept: `long` and `longSingle` also read `suspect_skip` cycles (S2); `short`, `variability`, `intermenstrual` read valid cycles only, so fixture B (one skipped log) raises no flag. (2) Variability needs six valid cycles, excludes warm-up cycles after stopping contraception or giving birth; age thresholds 7 d (26–41) and 9 d otherwise including unknown age (fewer flags). (3) Year 1 after menarche: no cycle-length flag at all. Teen (< 18) with no menarche year gets the 1–3-year adolescent thresholds (21/45). (4) "Fires at most once per 90 days" = `raisedOn` is stable for 90 days after the last raise (the UI persists it and only announces a flag whose `raisedOn` is today); a muted flag is hidden until the mute ends. Rejected: hiding the flag from the list after the first day (the Today card would vanish while the pattern persists). (5) Perimenopause: the long-cycle threshold becomes 60 days. (6) Missed period: `upper95` comes from the caller (predict) or is recomputed from valid cycles; the "from 40" 60-day rule is the gentler `missedFrom40`.
- D-020 (2026-10-09) `predict` wiring choices not fixed by the plan (P1-9). (1) Next-period confidence: `low` with fewer than 2 cycles in the model or an 80% half-width over 5 days; `high` only with ≥ 6 cycles and half-width ≤ 3 days; otherwise `medium`; then capped by the life-state gate. Fixture A is `medium` (the §9.6 "fair estimate"). (2) Prediction `basis` maps wearable → `bbt` and cervix → `combined` (the plan's `Prediction.ovulation.basis` union has no wearable/cervix member). (3) Phase: menstrual until the logged end of bleeding (default 5 days if none), `late` once past the 80% upper bound, `ovulatory` within ±1 day of the ovulation estimate, else follicular/luteal around it; with no ovulation estimate only menstrual/follicular/late. (4) Closed cycles get their ovulation from biomarkers inside the cycle; a stored estimate on the cycle is kept when there is no biomarker data (needed by fixture F). (5) `cycleLength.sd` is the predictive standard deviation (√ of the Student-t variance). Rejected: a confidence grade from SD[O] for the next period (that grade is for ovulation, §4.8).
- D-021 (2026-10-09) λ acceptance (P1-8, §4.15, V-05). Seeded backtest (`pnpm --filter @sanguine/backtest backtest lambda`, 4,000 users, wide population, step of +7 d after cycle 8, MAE over cycles 9–14): λ = 1 → 6.51 d, λ = 0.92 → 6.19 d, a 4.9% gain against the 15% required (+5 d: 4.7%, +10 d: 3.1%, +14 d: 2.5%). Clean-history MAE changes by +0.5% (within the 2% limit). Outcome: the plan's own fallback applies, `RECENCY_LAMBDA = 1` (`params.ts`), and `acceptance.test.ts` enforces "0.92 only if it passes, else 1". For reference λ = 0.8 gains 12% (λ = 0.7: 16.8%) with +1.9% clean cost, which is why the perimenopause gate keeps λ = 0.8, where a step change is the expected pattern. Rejected: shipping 0.92 on the plan's say-so (measured gain is a third of the gate).
- D-022 (2026-10-09) Backtest port (P1-8). `tools/backtest` is a TypeScript port of `proto.py` with a seeded RNG (mulberry32 + Box–Muller), so numbers differ from the Python run only by sampling noise. 4,000-user results for the shipped engine (λ = 1) reproduce §4.13 model D: clean, 8 cycles: MAE 2.66 (plan 2.6), 80% coverage 0.84 (plan 0.84), width 7.8; 8% skipped logs at 3 cycles: MAE 3.48 (plan 3.5); naive window coverage 0.59 (plan 0.59). Release-gate checks run in CI on 1,500 users (`acceptance.test.ts`). CSV replay (`backtest csv FILE`) takes period start dates only; LH-dated ovulation error needs donated data and is not built. Rejected: porting proto.py's numpy RNG stream exactly (not reproducible without NumPy).
- D-023 (2026-10-09) Data layer shape (P2-1). The `Database` interface is async (expo-sqlite is async-only); tests drive the same SQL through better-sqlite3 (`testDb.ts`, root dev dependency). Migrations are numbered TypeScript modules exporting the SQL string (`data/migrations/001_init.ts`) rather than `.sql` assets, because Metro would need a custom `sql` asset/transformer config that Expo Go does not need otherwise; the runner, numbering rules and transactional apply are unchanged. Append-only is enforced twice: by `BEFORE UPDATE`/`BEFORE DELETE` triggers on `event` and by the writer (P2-2). "Delete everything" therefore drops and recreates tables instead of deleting rows. `CHECK`s added to §5.2: `kind='retract'` iff `retracts` is set; `effective_day` date shape; quality/flow enumerations. `open(name, key?)` ignores `key` until P3-2.
- D-024 (2026-10-09) Event store (P2-2). (1) Projections are rebuilt in full after every write (`EventStore.rebuild`), matching §4.1 "recalculation is total"; cost is linear in the log and negligible for years of daily logs. (2) `retract` of a retract restores the target (active status is computed latest-first). (3) `daily_log` gained a `clots` column (heavy-bleeding flag needs it; §5.2 had no place for it); no real data exists yet so migration 001 was edited in place, later changes need migration 002+. (4) Period days = flow `light|medium|heavy` with `flow_kind = period`, plus `period.start` days; consecutive period days may be ≤ 2 days apart (one missing day); a lone `spotting` never starts a cycle. `period.end` overrides the run end. Cycle ids are `cyc-<start day>` so rebuilds are idempotent. (5) The §5.4 rule "a `period.start` within 7 days before an existing start merges into it; the UI confirms first" is a UI-time check (P2-9), not a projection rule: the projection stays a pure function of the log. (6) Profile (birth year, menarche year, usual length) lives in the `setting` table, not the log: it is mutable configuration, not a fact about a day. (7) `analyzeCycles` was exported from the engine for the projection and for the P2-3 ledger.
